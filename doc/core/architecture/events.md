# Event Catalog and AsyncAPI Documentation

> **Status**: 📋 Planned - This document outlines the future event documentation strategy

This document describes the event-driven architecture's event catalog and AsyncAPI documentation approach for the AI-powered recruitment system.

## Overview

The system uses **Apache Kafka** for event-driven communication between bounded contexts. This document provides:
- Inventory of all events and topics
- Event schemas and contracts
- Event flow diagrams
- AsyncAPI specifications (planned)
- Event catalog setup (planned)

## Event Architecture

### Event Types

The system uses two primary types of events:

**1. Change Data Capture (CDC) Events**
- Generated by Debezium from database transaction logs
- Low-level database change notifications
- Used for data synchronization between contexts
- Contain before/after values and metadata

**2. Business Events**
- Application-level domain events
- Published by services to indicate business state changes
- Higher-level abstraction than CDC events
- Consumed by business logic in other services

See [ADR-002: Event-Driven Architecture](../../adrs/002-event-driven-architecture.md) for architectural rationale.

## Event Inventory

### CDC Topics (Debezium)

#### Candidates Context CDC

**Topic**: `cdc.candidates.applications.applications`
- **Producer**: Debezium (Applications Database CDC Connector)
- **Purpose**: Captures changes to applications table
- **Consumers**: Applications Updater (Recruitment context)
- **Operations**: INSERT, UPDATE, DELETE
- **Schema**: Debezium envelope with application data

**Payload Fields:**
```json
{
  "before": null,  // Previous state (null for INSERT)
  "after": {       // New state
    "id": "uuid",
    "position_id": "uuid",
    "candidate_name": "string",
    "candidate_email": "string",
    "candidate_phone": "string",
    "resume_file": "string",
    "created_at": "timestamp"
  },
  "source": {
    "version": "string",
    "connector": "string",
    "name": "string",
    "ts_ms": 0,
    "snapshot": "boolean",
    "db": "string",
    "schema": "string",
    "table": "string"
  },
  "op": "c|u|d|r",  // Operation: create, update, delete, read
  "ts_ms": 0,
  "transaction": null
}
```

#### Recruitment Context CDC

**Topic**: `cdc.recruiters.positions.positions`
- **Producer**: Debezium (Positions Database CDC Connector)
- **Purpose**: Captures changes to positions table
- **Consumers**: Positions Publisher → Positions Service (Candidates context)
- **Operations**: INSERT, UPDATE, DELETE

**Topic**: `cdc.recruiters.positions.requirements`
- **Producer**: Debezium (Positions Database CDC Connector)
- **Purpose**: Captures changes to position requirements
- **Related Entity**: Positions

**Topic**: `cdc.recruiters.positions.responsibilities`
- **Producer**: Debezium (Positions Database CDC Connector)
- **Purpose**: Captures changes to position responsibilities
- **Related Entity**: Positions

**Topic**: `cdc.recruiters.positions.benefits`
- **Producer**: Debezium (Positions Database CDC Connector)
- **Purpose**: Captures changes to position benefits
- **Related Entity**: Positions

**Topic**: `cdc.recruiters.outbox`
- **Producer**: Debezium (Outbox Table CDC Connector)
- **Purpose**: Captures outbox events for transactional event publishing
- **Consumers**: Outbox Publisher (routes to business topics)
- **Pattern**: Transactional Outbox Pattern

See [ADR-003: CDC with Debezium](../../adrs/003-change-data-capture-debezium.md) and [ADR-004: Transactional Outbox](../../adrs/004-transactional-outbox-pattern.md).

**Topic**: `recruiters.positions`
- **Producer**: Positions Publisher (Kafka Streams transformation)
- **Purpose**: Business-level position change notifications
- **Consumers**: Positions Service (Candidates context)
- **Event Types**: PositionCreated, PositionUpdated, PositionDeleted
- **Schema**: Simplified business event (transformed from CDC)

#### Applications Domain

**Topic**: `candidates.applications.received`
- **Producer**: Applications Updater (via Outbox pattern)
- **Purpose**: Notify that new application received and ready for processing
- **Consumers**: Resume Analyzer Service
- **Trigger**: Starts the AI scoring pipeline
- **Guaranteed**: Exactly-once semantics via Outbox pattern

**Event Schema:**
```json
{
  "event_id": "uuid",
  "event_type": "candidates.applications.received",
  "timestamp": "2024-01-15T10:30:00Z",
  "data": {
    "application_id": "uuid",
    "candidate_id": "uuid",
    "position_id": "uuid",
    "candidate_name": "string",
    "candidate_email": "string",
    "resume_file": "string",
    "submitted_at": "timestamp"
  }
}
```

#### Scoring Domain

**Topic**: `recruiters.scoring.calculated`
- **Producer**: Scoring Service
- **Purpose**: Candidate-position matching score calculated
- **Consumers**: 
  - Insights Service (analytics aggregation)
  - Notifications Service (high-score alerts)
- **Contains**: Matching percentage and LLM explanation

**Event Schema:**
```json
{
  "event_id": "uuid",
  "event_type": "scoring.calculated",
  "timestamp": "timestamp",
  "data": {
    "application_id": "uuid",
    "candidate_id": "uuid",
    "position_id": "uuid",

      "percentage": 85.5,
      "explanation": "string (LLM-generated)",
      "similarity_score": 0.855,
      "calculated_at": "timestamp"
    }
  }
}
```

**Topic**: `recruiters.notifications`
- **Producer**: Notifications Service

**Event Schema:**

```json
    "candidate_name": "string",
```

## Schema Evolution Strategy

### Versioning Approach

**Semantic Versioning for Events:**
- **Major**: Breaking changes (remove fields, change types)
- **Minor**: Backward-compatible additions (new optional fields)
- **Patch**: Documentation or metadata changes

**Topic Versioning:**
- **Current**: Topics without version suffix (e.g., `recruiters.positions`)
- **Planned**: Version suffix for breaking changes (e.g., `recruiters.positions.v2`)

### Compatibility Rules

**Forward Compatibility** (Producers ahead of Consumers):
- Add optional fields only
- Never remove or rename fields
- Never change field types

**Backward Compatibility** (Consumers ahead of Producers):
- New consumers must handle missing fields gracefully
- Provide default values for new fields
- Maintain old message formats

**Full Compatibility**:
- Combination of forward and backward compatibility
- Safest for schema evolution
- Recommended for critical events

### Schema Registry Integration (Planned)

```yaml
# Producer Configuration
schema.registry.url: http://schema-registry:8081
```

## Best Practices

### Event Design

1. **Use descriptive event names**: `candidates.applications.received` (not `app.rec`)
2. **Include event metadata**: event_id, timestamp, version
3. **Keep events immutable**: Never update published events
4. **Design for idempotency**: Consumers should handle duplicates
5. **Include causation ID**: Link related events for debugging

### Schema Design

1. **Required fields only for critical data**: Avoid breaking changes
2. **Use semantic types**: UUID for IDs, ISO timestamps
3. **Document fields thoroughly**: Explain purpose and constraints
4. **Version schemas**: Track changes over time
5. **Test schema evolution**: Before deploying to production

### Error Handling

1. **Dead Letter Queues**: For poison messages
2. **Retry policies**: Exponential backoff
3. **Circuit breakers**: Prevent cascading failures
4. **Idempotent consumers**: Safe to replay events
5. **Monitoring and alerts**: Detect issues quickly
